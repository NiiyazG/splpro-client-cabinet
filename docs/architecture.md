# Целевая архитектура личного кабинета SPLPRO

## 1. Архитектурные принципы

1. **1С-first.** Коммерчески значимые сведения о контрагентах, номенклатуре, ценах, заказах, оплатах, взаиморасчётах, резервах и отгрузках исходят из 1С. Кабинет не создаёт параллельный мастер-справочник.
2. **Портал как слой взаимодействия.** Кабинет хранит UX-состояния, роли, настройки, чек-листы, файлы, комментарии и проекции данных для быстрого чтения.
3. **Событийное расширение.** Производственные стадии подключаются без изменения модели заказа через нормализованные события `ProductionStageChanged`.
4. **Идемпотентность и наблюдаемость.** Каждое сообщение имеет `eventId`, `source`, `occurredAt`, `entityId`, версию и correlation ID; повторная доставка не меняет результат.
5. **Минимизация персональных данных.** В портал передаются только данные, необходимые для сценариев клиента; секреты интеграций не попадают во frontend.
6. **External-selection only.** Подбор выполняется в конфигураторах сайта либо профильным инженером через заявку 1С; кабинет получает историю результатов по серверно подтверждённому subject текущего пользователя, хранит ссылку, внешний идентификатор, версию, источник и выбранную пользователем связь с объектом. Расчётного движка в домене кабинета нет.

```text
                    заказы, оплаты,      источник стадий
                    остатки, отгрузки    производства
```

## 4. Интеграция с 1С

### 4.1 Направления обмена

**1С → кабинет:** контрагенты и договоры; номенклатура; индивидуальные условия; заказ и позиции; счета/оплаты; резервы; плановые даты; складская готовность; реализации и отгрузки; ссылки на печатные формы.

**Кабинет → 1С:** заявка менеджера на инженерный подбор и её дополнения; заявка/черновик заказа после валидации; запрос резерва; подтверждение спецификации; выбранное окно поставки; реквизиты доставки; уточнение назначения платежа; запрос отмены; результат клиентского действия. Запись проводится в 1С асинхронно и получает технический и бизнес-статус.

### 4.2 Контракт интеграции

- REST/JSON через защищённый integration gateway либо брокер сообщений — по возможностям используемой конфигурации 1С.
- Версионирование `/api/integration/v1` и JSON Schema/OpenAPI для каждого контракта.
- Идемпотентный ключ: `<source>:<entityType>:<entityId>:<version>`.
- Optimistic locking по `sourceVersion`.
- Inbox фиксирует получение, outbox — гарантированную публикацию локальных изменений.
- Retry: экспоненциальная задержка; после лимита — DLQ и задача оператору.
- Периодическая сверка контрольных сумм и количества сущностей за период.
- Интерфейс показывает время актуальности и деградированный режим, а не скрывает сбой.

### 4.3 Целевая свежесть

| Данные | Цель |
|---|---|
| статус/срок заказа, оплата, готовность к отгрузке | до 5 минут |
| справочники и договоры | до 30 минут |
| аналитические витрины | до 60 минут |
| критические изменения срока | push-событие и уведомление до 5 минут |

## 5. Чек-листы заказчика

Чек-лист отделён от жёсткой схемы заказа.

```text
ActionTemplate → ActionInstance → ActionEvidence / ActionComment
```

`ActionTemplate`: тип оборудования, стадия, роль-исполнитель, название, инструкция, обязательность, правило срока, требуемый тип подтверждения.

`ActionInstance`: заказ, объект, исполнитель, `status`, `dueAt`, `blocking`, `source`, связь с внешней задачей.

Статусы: `not_started → in_progress → submitted → accepted`; альтернативы: `rejected`, `waived`, `overdue`, `cancelled`.

Первый этап — ручные шаблоны сотрудников SPL. Второй — автоматическое создание по типу заказа и стадии. Третий — правила из 1С/MES и контроль блокирующих зависимостей.

## 6. Модель производственных стадий

Заказ содержит не фиксированный набор колонок, а экземпляр процесса:

```text
ProductionProcess
 ├─ processTemplateId / version
 ├─ sourceSystem
 ├─ progressPercent / forecastReadyAt
 └─ ProductionStageInstance[]
       code, name, sequence, status,
       plannedStart/Finish, actualStart/Finish,
       publicDescription, delayReasonPublic
```

События: `ProductionProcessCreated`, `ProductionStageStarted`, `ProductionStageProgressed`, `ProductionStageCompleted`, `ProductionForecastChanged`, `ProductionIssuePublished`, `OrderReadyForShipment`.

Внешние технические коды сопоставляются с публичной таксономией. Клиент не видит внутренние операции, коммерческую тайну и персональные данные сотрудников производства.

## 8. Хранение и инфраструктура

- PostgreSQL — транзакционные данные кабинета и read-модели.
- S3-совместимое хранилище — документы, только через короткоживущие signed URL.
- Redis — сессии, кэш, rate limits; не источник истины.
- RabbitMQ/Kafka — события при наличии зрелой эксплуатации; на MVP допустима очередь в интеграционном контуре.
- OpenTelemetry + централизованные логи/метрики/трейсы.
- Контейнерное развёртывание: два экземпляра API за балансировщиком, stateless frontend/API.

## 9. Безопасность

- OIDC/OAuth 2.1, MFA для администраторов организаций и сотрудников SPL.
- Tenant isolation: `organization_id` проверяется сервером во всех запросах; идентификатор из клиента не считается доказательством доступа.
- RBAC дополняется проверками объекта/проекта и назначения пользователя.
- TLS, шифрование резервных копий, секреты в vault, ротация ключей.
- Антивирусная и MIME-проверка файлов; запрет исполняемого содержимого.
- CSRF-защита для cookie-сессий; CSP, HSTS, secure/httpOnly/sameSite cookies.
- Аудит входов, прав, согласований, скачивания чувствительных документов и интеграционных команд.
- Требования 152-ФЗ: основания обработки, сроки хранения, удаление/обезличивание, локализация по принятой юридической модели.

## 10. Отказоустойчивость и восстановление

- Цель доступности после MVP: 99,9% в месяц без учёта согласованных окон.
- RPO ≤ 15 минут, RTO ≤ 4 часов — уточнить после классификации данных.
- Деградация 1С: просмотр последней успешной проекции с явным временем актуальности; команды ставятся в очередь или блокируются согласно риску.
- Деградация MES: сохраняется последний таймлайн; показывается предупреждение, прогноз не пересчитывается.
- Ежедневные резервные копии плюс PITR; квартальная проверка восстановления.

## 11. Поставка по вертикальным срезам

1. SSO, организации, роли, read-only объекты/заказы из 1С, журнал обмена.
2. Ролевые дашборды и клиентские чек-листы с ручными шаблонами.
3. Внешний конфигуратор → импорт результата → объект → черновик заказа → 1С.
4. Поставки, документы, уведомления и клиентские подтверждения.
5. Производственный таймлайн через нормализованный событийный контракт.
6. Управленческая аналитика и прогнозы после стабилизации качества данных.
